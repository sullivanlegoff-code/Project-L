# Backend privé — configuration nécessaire

Statut : SQL et client préparés ; aucun projet Supabase ni email réel vérifié dans cet environnement. Ne pas annoncer de sauvegarde en ligne tant que les vérifications hébergées ci-dessous n'ont pas réussi. Le jeu `production` existant reste jouable sans compte.

## Actions accessibles au propriétaire, sans communiquer de secret

1. Se connecter sur https://supabase.com/dashboard et créer un **nouveau projet Free**, dans une organisation Free. Choisir une région proche. Garder le mot de passe de base dans un gestionnaire de mots de passe ; ne pas le copier dans GitHub, le jeu ou cette conversation. Ne pas activer d'option payante.
2. Dans **SQL Editor → New query**, copier [001_private_saves.sql](migrations/001_private_saves.sql) en entier, puis Run **une fois**, sur ce nouveau projet vide. Le fichier est transactionnel et n'efface aucune ancienne partie. `prairie_private` doit rester absent des **schémas exposés** de la Data API ; seul `public` est nécessaire.
3. Dans **Authentication → Sign In / Providers → Email**, activer Email et autoriser les inscriptions. Dans **URL Configuration**, Site URL et Redirect URLs = `https://sullivanlegoff-code.github.io/Project-L/preview/accounts/`. Le dashboard du propriétaire exige maintenant un SMTP personnalisé pour modifier le template : **garder le modèle par défaut et son lien de connexion pour le premier essai gratuit**. Le client traite le retour par le SDK officiel, sans sélectionner/écraser automatiquement la partie. Un code numérique est une option ultérieure : avec SMTP configuré, template Magic Link contenant `{{ .Token }}`, longueur 6–10 chiffres. Aucun abonnement nécessaire uniquement pour modifier le modèle à cette étape.
4. Pour le premier essai gratuit, utiliser une adresse appartenant déjà à l'équipe de l'organisation Supabase. L'envoi intégré **refuse les autres adresses** et est très limité, sans garantie de livraison. Ne pas inviter de joueurs comme administrateurs pour contourner cette limite. Pour accueillir d'autres joueurs, configurer **Authentication → SMTP Settings** avec un fournisseur SMTP autorisé : serveur, port, expéditeur validé et identifiants saisis **uniquement dans Supabase**. Aucun fournisseur ou abonnement payant n'est configuré ici. La disponibilité d'un expéditeur/domaine existant et les limites du fournisseur restent à vérifier avant ce choix.
5. Dans **Connect / Project Settings → API Keys**, relever seulement **Project URL** et la clé **publishable** commençant par `sb_publishable_`. Elles sont publiques, prévues pour le navigateur. Ne jamais utiliser `sb_secret_`, `service_role`, mot de passe de base, token Management API ou mot de passe SMTP dans le client.
6. Dans GitHub : **Project-L → Settings → Secrets and variables → Actions → Variables → New repository variable**, créer `PRAIRIE_PREVIEW_SUPABASE_URL` et `PRAIRIE_PREVIEW_SUPABASE_PUBLISHABLE_KEY` avec ces deux valeurs publiques. L'intégration actuelle reçoit HTTP 403 sur l'administration des variables ; le propriétaire doit effectuer cette étape dans l'interface. Relancer **Actions → Publier Prairie de lapins → Run workflow → production**. Le projet choisi sera utilisé **uniquement par la prévisualisation** ; le jeu normal et le laboratoire restent locaux. La prévisualisation ne copie aucune partie normale.

La version normale avec comptes ne sera livrée qu'après connexion email et validations réelles de deux comptes/contextes. Les variables de prévisualisation n'activent pas les comptes dans le jeu normal. Un backend de test séparé est préférable ; les identifiants/local caches sont isolés aussi par projet Supabase.

## Vérifications hébergées encore indispensables

- Recevoir puis vérifier un vrai code sur une adresse de test autorisée ; tester code faux/expiré, quota, renouvellement de session et déconnexion.
- Compte A : transfert explicite d'une sauvegarde fictive ; autre navigateur privé : chargement distant explicite puis action et retour A. Compte B : vérifier directement via la Data API que la lecture filtrée sur A renvoie zéro ligne (RLS), que l'historique A est invisible et qu'une écriture RPC avec `p_owner=A` est refusée. Aucun test ne doit utiliser la partie personnelle.
- Anonyme : tables et RPC refusés ; authentifié : INSERT/UPDATE/DELETE directs refusés ; seul le RPC conditionnel autorise les écritures propres.
- Deux contextes modifient la même révision : une seule écriture gagne, l'autre conserve sa partie et propose les deux versions. Annuler puis confirmer une résolution ; retrouver la version remplacée dans l'historique.
- Bloquer le réseau après une action, vérifier le cache puis rétablir ; réponse perdue, session expirée, changement de compte avec requête retardée ; aucune écriture dans l'autre compte. Import/restore créent une nouvelle révision, préservent l'ancien état et les récompenses.

Les tests PGlite exécutent les véritables fonctions SQL et permissions PostgreSQL. Ils ne remplacent pas la vérification des JWT, du schéma Data API et du SMTP sur le service géré.

## Conservation, versions et opérations

Par propriétaire : union des **20 dernières révisions**, du **premier état synchronisé de chacun des 7 derniers jours UTC ayant eu une sauvegarde**, et des **20 derniers points explicites** avant import/remplacement/restauration/reset. Union : au plus 47 états historiques plus l'état courant. Certaines dates anciennes peuvent aussi rester représentées dans les 20 dernières révisions ; ce n'est pas une suppression stricte après sept jours. Les 64 dernières opérations conservent leurs empreintes et accusés, pas une copie d'état supplémentaire. Une répétition plus ancienne échoue par contrôle de révision et demande un choix ; elle ne redevient pas une nouvelle écriture silencieuse. Les points en attente locaux sont limités à 20, plus les points déjà figés dans un envoi en attente (au plus 20).

Réglages serveur dans `prairie_private.retention`, via SQL Editor uniquement : `revisions=20`, `active_days=7`, `checkpoints=20`, `operations=64`. Les bornes autorisées sont contrôlées en base ; ajuster ensemble le budget et la limite de lecture du client (150 historiques). Pas de modification depuis le navigateur.

L'état JSON reste v4 ; les révisions et dates serveur sont autour de cet état. Le serveur borne/contrôle la structure, les ressources, propriétaires et références essentielles ; le client applique **la validation complète existante des missions, habitats, délais, réservations et récompenses** avant envoi et après lecture. Une sauvegarde incompatible est mise en quarantaine. Une future migration doit modifier format, RPC et lecteurs ensemble ; un client v4 ne peut pas écraser une ligne de format supérieur. Un état courant corrompu administrativement peut nécessiter une réparation contrôlée du backend ; aucun reset automatique ne le remplace.

Le serveur ne fait pas autorité sur les règles de jeu et ne protège pas contre la triche du propriétaire de sa propre partie. Ce prototype n'est pas compétitif. RLS et RPC protègent la confidentialité entre comptes et les écritures concurrentes, pas contre un script malveillant exécuté sur la même origine.

Free : deux projets actifs au total dans les organisations où l'on est propriétaire/admin ; 500 Mo de base par projet, 5 Go d'egress, 50 000 utilisateurs actifs/mois et 1 Go de fichiers. Ces quotas ne sont pas une garantie de conservation ou disponibilité. La base des parties consomme les 500 Mo, pas le stockage de fichiers. Maximum serveur 1 Mo par état / 4 Mo de points par requête, donc le plafond de 47 états par compte n'autorise pas un nombre illimité de joueurs. Surveiller les usages et conserver les exports. Aucun passage payant automatique prévu.

L'historique du jeu reste dans le même projet ; les backups automatiques quotidiens de base sont une offre payante. Un export JSON dans Fichiers est un secours **indépendant** du service et du navigateur. Ne pas supprimer un projet sans exports ; les sauvegardes du projet sont aussi concernées. Le SMTP intégré est réservé à l'équipe, à quota variable très bas et best effort ; les quotas exacts doivent être relevés dans le dashboard, pas supposés stables. Une offre Free peut imposer une pause ; vérifier la politique affichée au moment de créer le projet.
